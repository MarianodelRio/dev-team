# dev-team — CLAUDE.md

## What is dev-team?

**dev-team** is a framework for building software with a team of AI agents via parallel
spec-driven development. Starting from a vague idea or an existing codebase, it guides
you through design and planning, then executes the implementation using specialized
agents working in parallel — each owning their module, each enforcing quality.

Single source of truth: git. No external services, no databases, no dashboards.

---

## How it works

```
IDEA.md  →  /bootstrap  →  design.md + spec.md + plan.md + tasks/  →  /orchestrate  →  /done
```

1. **Write your idea** in `IDEA.md` (as vague as you want)
2. **Run `/bootstrap`** — conversational design session, generates architecture + tasks + infra
3. **Run `/orchestrate`** — picks the best available task, analyzes it, plans, codes, reviews, and opens a PR automatically
4. **Merge on GitHub, run `/done T-XXX`** — marks done, cleans the branch (if `cleanup_merged_branches: true`), reports what's unblocked

## Folder structure

```
IDEA.md                    ← your project idea (fill this first)
CLAUDE.md                  ← this file — human documentation and framework rules
devteam.config.yml         ← framework configuration
design.md                  ← architecture, modules, contracts (generated by /bootstrap)
spec.md                    ← module behavioral specs (generated by /bootstrap, edit only via /refine)
plan.md                    ← phases and dependency graph (generated by /bootstrap)

scripts/                   ← dt-claim, dt-ready, dt-pr, dt-verify, dt-done, dt-cancel, dt-restart, dt-board

.claude/
  commands/                ← skills (/bootstrap, /orchestrate, /prepare-pr, etc.)
  agents/                  ← framework agents (pre-existing): orchestrator, architect, planner, coder,
                              advisor, review-coordinator, and up to 6 sub-reviewers; project agents
                              (generated by /bootstrap): domain-specific agents for your modules
  AGENTS.md                ← stub (content moved to .claude/steering/)
  steering/                ← scoped steering files (always.md, task-format.md, context-formats.md, coder-complete.md)
  settings.json            ← sub-agent spawn depth and concurrency (required by the review pipeline)

tasks/
  available/               ← TODO + all dependencies DONE
  in-progress/             ← currently being worked on
  ready-for-pr/            ← escape hatch only (tasks not processed by /orchestrate Phase 4)
  pr-open/                 ← PR open on GitHub
  done/                    ← merged
  blocked/                 ← dependencies not yet DONE
  cancelled/               ← cancelled tasks (audit trail — never picked up by /orchestrate)

context/
  decisions/               ← per-task decision logs (context/decisions/T-XXX.md)
  discoveries/             ← per-task cross-agent alerts (context/discoveries/T-XXX.md)
  retrospectives/          ← persistent lessons by role (context/retrospectives/{coder,planner,architect}.md)

docs/                      ← project documentation (API, ADRs, architecture)

tests/
  fixtures/                ← smoke test fixtures and test doubles (no real network calls)
```

## Task lifecycle

```
available/ → in-progress/ → pr-open/ → done/
```

Status lives in the task file's YAML frontmatter. Moving between folders is the visual
signal — frontmatter is the machine-readable source of truth.

### Task file format

```markdown
---
id: T-001
phase: 0
agent: backend
depends_on: []
status: available
folders: [apps/api/, libs/auth/]
outputs:
  - "POST /auth/login → {token: string, expires_at: ISO8601}"
  - "GET /auth/token → {valid: bool, user_id: string}"
size: M
branch: ~
pr: ~
---

## Title

**Scope:** what modules this touches.

**Delivers:**
- specific function or endpoint
- another deliverable

**Implementation done when:**
- [ ] acceptance criterion 1
- [ ] tests written and passing (types per the Testing strategy in `design.md`)

**Task done when (post-review):**
- [ ] PR merged into main
- [ ] primary doc updated (the file named in the Documentation plan — e.g. `docs/api.md`, `docs/cli.md`, `docs/usage.md`)
```

Max 150 words in the body. Checklists, not prose.

**Task size guide:**
- `size: S` — ≤4h, single file or function
- `size: M` — 4-16h, multiple files within one module
- `size: L` — >16h, cross-module or cross-service changes

After completing a task, the agent appends:

```markdown
## Completed
- What was implemented
- What changed from the original plan
- Decisions made and why
```

## Framework agents

**Framework agents** (orchestrator, architect, planner, coder, advisor, review-coordinator, and up to six sub-reviewers) are pre-existing and ship with dev-team. **Project agents** are generated by `/bootstrap` and provide domain-specific roles (e.g., `backend`, `frontend`) tailored to your modules.

### Agent file format

Every file in `.claude/agents/` **must** declare `name` and `description` in its frontmatter.
Claude Code registers a file as an invocable sub-agent type only when both are present — a file
carrying just `model:` is silently ignored, the spawn falls back to a generic agent with the
definition pasted inline, and the per-agent model routing below is lost. Nothing reports an error
when this happens, so treat the frontmatter as load-bearing, not metadata.

```markdown
---
name: review-coordinator        # exactly the filename without .md
description: Runs the full review pipeline for a PR and returns one consolidated report. Invoked in Phase 4 of /orchestrate and by /prepare-pr.
model: claude-sonnet-5
---
```

- `name` — must match the filename character for character. Every spawn (`/orchestrate` Phases 1–4,
  `/prepare-pr`) and every `agent:` field in `tasks/*.md` resolves by this string.
- `description` — one line stating **what** the agent does and **when** to invoke it. Claude Code
  reads it to judge relevance; it is not decorative.
- `model` — per-agent routing. `/team-init` Section E rewrites this field; it must not touch the
  other two.

Nested spawning (review-coordinator → reviewers) requires `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH: "2"`
in `.claude/settings.json`. Without it the review pipeline cannot launch its sub-reviewers.

### Coordinator
- `orchestrator` — coordinates all 5 phases of /orchestrate, /bug, and /explore (Phase 0: config extraction, Phase 1: analysis, Phase 2: planning, Phase 3: implementation, Phase 4: review). Sole point of contact with the user during task execution.

### Analysis (Phase 1)
- `architect` — validates the task against current project state, guards shared contracts, maintains the DAG, writes ADRs.

### Implementation (Phases 2–3)
- `planner` — converts the approved task into a concrete plan of files and functions.
- `coder` — implements the plan in the assigned worktree, writes tests, verifies quality.

### Shared resource
- `advisor` — senior technical consultant with an opinionated recommendation. Any agent can invoke it.

### Review (Phase 4, via review-coordinator)
- `review-coordinator` — manages the review pipeline; spawned by the Orchestrator, coordinates parallel sub-agents and returns a consolidated report.
  - `code-quality` — scope, architecture, tests, docs.
  - `security` — OWASP Top 10 on the diff.
  - `adversarial` — receives a compact manifest of the other agents' findings (not full outputs); looks for what the others missed.
  - `smoke-tester` — runs the app, validates acceptance criteria.
  - `mutation-tester` — verifies test quality by checking if tests catch artificially introduced bugs; only run on critical modules.
  - `spec-coverage` — maps spec.md Logic+Interface constraints to tests in the PR diff; advisory only, never blocks; only run when `spec_coverage_enabled: true`.

## Branch naming

```
main                          ← always stable, all checks passing
feature/T-XXX-short-slug      ← one branch per task
fix/B-XXX-short-slug          ← one branch per bug task
```

> **Requirement:** `main` must **not** be a protected branch. The framework pushes
> `tasks/*.md` status metadata directly to `main` as its coordination mechanism
> (`/orchestrate`, `/done`, `/add-task`, `/bug`). Branch protection on `main` will
> make these pushes fail and break the workflow. If your org requires protection,
> exclude `tasks/**` from the ruleset — otherwise leave `main` unprotected.
>
> **Enterprise alternative:** If `main` must be fully protected, either:
> 1. Use a bot account with bypass permissions for the `dt-*` scripts
> 2. Store task metadata on a separate `dt-metadata` branch (requires framework modification)

## spec.md

Bridge between `design.md` (architecture) and `tasks/` (work units). Contains one section per module:

- **What it does** — 1-2 sentences, the "what" not the "how"
- **Logic** — non-obvious business rules, edge cases, failure modes
- **Interface** — inputs (source + format), outputs (destination + format), errors raised
- **Out of scope** — what this module deliberately does not handle

A "Cross-module flows" section traces each significant user-facing flow step-by-step.

Generated by `/bootstrap` after plan approval and before task generation. In brownfield mode, generated from the existing code.

**Never edit `spec.md` directly — use `/refine`.** `/refine` classifies affected tasks by state and propagates changes safely: modifying available/blocked tasks, writing discoveries for in-progress tasks, and creating retrofit tasks for completed modules.

## Available commands

| Command | What it does |
|---------|-------------|
| `/team-init` | Configure the project and show current state — run this first |
| `/bootstrap` | Conversational setup: idea → design → plan → tasks → infra |
| `/orchestrate [T-XXX]` | Pick next task, analyze, plan, code, review, and open a PR automatically |
| `/bug [description]` | Investigate a bug, find root cause, create fix task |
| `/explore [topic]` | Investigate an implementation or behavior in the project |
| `/done T-XXX` | Mark DONE after merge, report unblocked tasks |
| `/add-task [description]` | Design and add a new task mid-project |
| `/status` | Full project status board |
| `/cheatsheet` | What to do next, contextual to the current board (global or per-task) |
| `/guide` | Current state of the project — what's built, how to test it |
| `/restart T-XXX` | Recover a task stuck in-progress (agent crashed, worktree lost) |
| `/reopen T-XXX` | Move a task back to available after its PR is rejected or closed without merging |
| `/cancel T-XXX` | Abandon a task cleanly |
| `/prepare-pr T-XXX` | Manual escape hatch for tasks in ready-for-pr outside normal flow |
| `/refine [description]` | Update spec.md with state-aware propagation to affected tasks |

## Configuration

All framework behavior is controlled by `devteam.config.yml`. See that file for all options with inline documentation. Options marked `PLANNED: not yet implemented` in the config file are parsed but have no effect in the current version. Valid values for all enum-type settings (`pr_mode`, `human_checkpoint`, `require_advisor`, `auto_merge`, `review_profile`, `smoke_test_mode`) are documented as inline comments directly in `devteam.config.yml`.

## Key rules

- **Each agent owns specific folders** — defined in `.claude/agents/[name].md`; it never writes outside them
- **Protected files** (shared contracts, database schema, CI/CD config) require explicit human approval before any agent touches them; changes must be propagated to all consuming modules in the same PR
- **Never edit `spec.md` directly** — use `/refine`
- **Never commit directly to `main`** — only `tasks/*.md` status updates go to main; all implementation goes through feature branches
- **Never skip the human checkpoint** — the Orchestrator presents the plan and waits for confirmation before any code is written

Agent-specific runtime rules are defined in `.claude/steering/`. The `inclusion:` frontmatter in each
file documents its intended scope; **the Orchestrator is what actually relays them** — it reads the
files in Phase 0 and pastes the relevant ones inline at the top of each sub-agent prompt (the
review-coordinator forwards them again to the reviewers it spawns). There is no automatic harness-side
injection, so an agent invoked outside `/orchestrate` receives no steering.
- `always.md` and `task-format.md` — relayed to every agent
- `context-formats.md` — relayed to orchestrator, architect, coder, and planner
- `coder-complete.md` — relayed to the coder only
