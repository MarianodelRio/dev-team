# ADR 0004 — spec.md: Module Behavioral Specification

**Date:** 2026-08-05
**Status:** Accepted

## Context

`design.md` describes architecture at a module-boundary level: what modules exist, how they communicate, what technology they use. `tasks/` describes work units at a function/file level: what to implement, what tests to write, what acceptance criteria to meet.

The gap between these two levels caused recurring problems:

- Planners had to interpret high-level architecture into specific module behavior with no canonical source for edge cases, failure modes, or business rules
- A behavior change affecting multiple tasks had no single update point — editing individual tasks was error-prone and left others stale
- Parallel tasks working on related modules could make inconsistent behavioral assumptions that only surfaced during integration

## Decision

Introduce `spec.md` between `design.md` and `tasks/` in the project artifact hierarchy.

`spec.md` has one section per module specifying:
- What the module does (1-2 sentences — the "what", not the "how")
- Non-obvious logic: business rules, edge cases, how failures are handled
- Interface: inputs (source + format), outputs (destination + format), errors raised
- What is explicitly out of scope

A "Cross-module flows" section traces each significant user-facing flow step-by-step through the modules it touches.

`spec.md` is generated by `/bootstrap` after plan approval and before task generation. After initial generation, it is modified exclusively via `/refine`.

`/refine` is state-aware: for each task affected by a spec change, it applies the right action based on the task's current status — modifying available/blocked tasks directly, writing discoveries for in-progress tasks, and creating retrofit tasks for completed modules.

The Architect validates task scope against `spec.md` in Phase 1 of `/orchestrate`. The Planner receives the relevant module sections as input and produces plans consistent with the spec.

## Consequences

- One canonical source for "what should this module do" — behavioral questions are no longer inferred from architecture
- Planners produce more accurate implementation plans with fewer ambiguous decisions
- Behavioral scope creep is caught in Phase 1 before code is written
- Mid-project behavioral changes propagate consistently to all affected tasks via `/refine`
- `spec.md` requires maintenance: it reflects decisions at generation time; `context/decisions/` records what changed during implementation and why — these two are complementary

## Discarded

**Extending design.md with behavioral detail:** design.md would mix architecture decisions with implementation behavior, growing very large and losing its role as the architectural reference.

**Embedding behavior in task files:** behavior is often shared across tasks and module boundaries; task-level notes do not generalize, and updating them independently creates inconsistency.

**No intermediate artifact (current state):** agents infer behavior from architecture, leading to inconsistencies across parallel tasks with no mechanism to propagate behavioral changes mid-project.
